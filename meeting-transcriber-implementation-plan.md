# План реализации локального сервера транскрипции совещаний

## 1. Цель проекта

Подготовить в текущей рабочей директории самостоятельный репозиторий для полностью локальной транскрипции аудиозаписей совещаний.

Система должна:

- распознавать русскую речь с частыми английскими техническими терминами;
- определять говорящих на совещаниях с ориентировочно 8–15 участниками, без жёсткого ограничения в 4 участника;
- корректно обрабатывать обычные перебивания и частичное наложение речи;
- сохранять временные метки реплик и, по возможности, отдельных слов;
- исправлять очевидные ошибки распознавания технических терминов с помощью контекстного словаря;
- формировать исходную транскрипцию, исправленную транскрипцию и протокол совещания;
- запускаться на Linux-сервере с NVIDIA GPU, в том числе на GPU с 8 ГБ VRAM при последовательном выполнении тяжёлых этапов;
- разворачиваться через Docker с поддержкой NVIDIA Container Toolkit;
- работать в полностью автономном режиме после предварительной загрузки моделей и зависимостей.

Результат работы агента — готовый репозиторий в текущей директории: загрузка моделей, установка/сборка окружения, скрипты инференса, единый pipeline, Dockerfile, Compose-конфигурация, документация и тесты.

## 2. Обязательные правила исследования и работы агента

### 2.1. Использование MCP

При исследовании моделей и параметров их запуска обязательно использовать **Hugging Face MCP**, если возникают вопросы о:

- доступных моделях и вариантах checkpoint;
- назначении, языковой поддержке и ограничениях модели;
- лицензии и условиях использования;
- формате весов и способе загрузки;
- рекомендуемых параметрах инференса;
- совместимости модели с GPU и объёме памяти;
- актуальности и статусе репозитория модели.

При вопросах о том, **как использовать программные библиотеки и API инференса**, обязательно использовать **DeepWiki MCP** для изучения соответствующих исходных репозиториев и документации, например:

- NVIDIA/NeMo;
- SYSTRAN/faster-whisper или ggml-org/whisper.cpp;
- PyTorch;
- FFmpeg;
- других библиотек, которые агент решит включить.

Не выдумывать имена API, аргументы CLI, конфигурационные ключи и форматы checkpoint. Проверять их по документации и исходному коду через DeepWiki MCP и, при необходимости, по официальной документации проекта.

Если MCP недоступен, явно зафиксировать это в отчёте, использовать официальную документацию/исходный репозиторий как резервный источник и не выдавать непроверенные сведения за подтверждённые.

### 2.2. Принцип автономности

Ключевое требование: **Hugging Face MCP используется агентом только как исследовательский инструмент во время разработки. Он не должен становиться зависимостью создаваемого сервера.**

В готовой системе:

- не должно быть обязательных HF-токенов;
- не должно быть обращений к Hugging Face Hub во время инференса;
- не должно быть автоматической загрузки моделей при старте контейнера;
- все модели должны загружаться отдельными явными скриптами и храниться локально;
- инференс должен работать без доступа к интернету;
- при отсутствии локальной модели приложение должно завершаться с понятной ошибкой, а не пытаться скачать её;
- предусмотреть offline-проверку, например через `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` там, где эти переменные применимы, и сетевой запрет на уровне Docker/тестового окружения.

Не добавлять Hugging Face token в `.env`, Docker image, Compose или конфигурацию runtime. Если конкретный выбранный checkpoint требует принятия условий, авторизации или gated-доступа для первоначального получения, это должно быть явно указано в документации. По возможности выбрать альтернативный checkpoint с открытой прямой загрузкой из официального источника.

### 2.3. Сначала исследование, затем реализация

До написания основного кода агент должен:

1. Изучить актуальные модели и официальные инструкции.
2. Проверить реальные ограничения по языкам, числу говорящих, длине аудио и VRAM.
3. Зафиксировать выбранные версии библиотек и checkpoint.
4. Составить краткий ADR (Architecture Decision Record) с обоснованием выбора.
5. Только после этого реализовывать систему.

Не считать ранее предложенные в обсуждении названия моделей и параметры безусловно подтверждёнными: перепроверить их по актуальной документации. В частности, проверить, подходит ли конкретный multilingual VAD checkpoint, TitaNet checkpoint и выбранный метод clustering для русскоязычных записей.

## 3. Предлагаемая архитектура

Система должна быть модульной, с независимыми компонентами и явными контрактами данных.

### 3.1. Audio preprocessing

Назначение:

- чтение WAV, MP3, M4A, FLAC и других форматов, поддерживаемых FFmpeg;
- проверка длительности, числа каналов, sample rate и повреждений;
- преобразование в формат, требуемый выбранными моделями;
- сохранение исходного аудио без изменений;
- создание производной mono-версии для моделей, если это требуется;
- не выполнять агрессивное шумоподавление по умолчанию, поскольку оно может ухудшить распознавание и diarization.

Использовать FFmpeg как отдельную системную зависимость. Параметры ресемплинга и сведения о каналах сохранять в metadata.

### 3.2. ASR — распознавание речи

Основной кандидат для MVP:

- Whisper large-v3-turbo;
- inference backend выбрать после сравнения `faster-whisper` и `whisper.cpp`;
- русский язык задавать явно;
- поддерживать английские фрагменты и смешанную русско-английскую речь;
- получать сегменты и word-level timestamps, если выбранный backend это поддерживает;
- сохранять исходный текст ASR без последующей коррекции.

Не считать, что `initial_prompt` гарантированно решает распознавание технических терминов. Исследовать поддержку prompt/context у выбранного backend и ограничения по длине/эффекту подсказки.

Обязательно предусмотреть возможность заменить ASR backend без изменения остального pipeline. Для этого определить интерфейс `Transcriber`.

Кандидат для сравнительного тестирования — Qwen3-ASR, но включать его в MVP только после проверки качества русского языка, лицензии, способа локальной загрузки, потребления VRAM и зрелости inference-инструментария.

### 3.3. Speaker diarization — определение говорящих

Основной кандидат — каскадная diarization-система NVIDIA NeMo, а не модель с фиксированным лимитом в четыре говорящих.

Исследовать и проверить конкретную конфигурацию из следующих типов компонентов:

- VAD, например подходящий multilingual MarbleNet checkpoint;
- speaker embeddings, например TitaNet-Large;
- clustering, например spectral clustering;
- оценка числа говорящих автоматически либо настройка известного диапазона;
- обработка коротких реплик, тишины и частичного наложения речи.

Требования:

- целевой сценарий — 8–15 участников;
- поддерживать настройку `max_num_speakers` с разумным запасом, например 20, если это поддерживается выбранной версией;
- не задавать число участников равным 15 автоматически: предпочтительно автоматическое определение с ограничением сверху;
- позволять вручную указать известное число участников;
- сохранять confidence/score, если модель его предоставляет;
- не обещать точное разделение одновременной речи, если выбранный алгоритм не поддерживает overlap-aware diarization.

Агент должен проверить точные имена checkpoint, конфигурационные поля, формат `.nemo` и API текущей версии NeMo через DeepWiki MCP и официальные источники.

Nemotron-3-Diarization можно оценить как альтернативный кандидат, но не включать автоматически: сравнить зрелость интеграции, возможности для 8–15 участников, формат входов/выходов, требования к GPU и простоту полностью локального развёртывания.

Определить интерфейс `Diarizer`, чтобы можно было заменить реализацию без изменения pipeline.

### 3.4. Alignment и fusion

Компонент объединяет ASR и diarization:

- сопоставляет слова/сегменты ASR с временными интервалами говорящих;
- назначает `speaker_id` каждой реплике;
- учитывает небольшие расхождения временных меток;
- не приписывает слово говорящему, если соответствие неоднозначно;
- поддерживает участки с перекрывающейся речью, если diarization возвращает несколько активных говорящих;
- сохраняет исходные временные метки и происхождение каждого результата.

Если ASR и diarization используют разные сегментации, реализовать отдельный алгоритм пересечения временных интервалов. Не пытаться «исправить» diarization только на основании текста.

### 3.5. Terminology Engine — техническая терминология

Это обязательный компонент, поскольку совещания могут содержать русскую речь с английскими техническими терминами, названиями библиотек, классов, функций, алгоритмов и продуктов.

Создать локальный словарь с версионированием. Формат MVP — YAML или JSON.

Пример:

```yaml
terms:
  - canonical: vtkChartXY
    aliases:
      - vtk chart xy
      - витэка чарт икс уай
    category: class
    project: granum

  - canonical: dirty flag
    aliases:
      - дирти флаг
      - dirty-флаг
    category: concept

  - canonical: CMake
    aliases:
      - си мейк
    category: tool
```

Функции компонента:

1. Нормализация регистра и пунктуации без разрушения идентификаторов.
2. Поиск вариантов написания и транслитерации.
3. Fuzzy/phonetic matching для вероятных ASR-ошибок.
4. Контекстное ранжирование кандидатов.
5. Исправление только при достаточной уверенности.
6. Сохранение исходного текста и журнала всех исправлений.
7. Возможность отключить автоматическую замену и выводить только предложения.
8. Поддержка нескольких профилей словарей.

Профили, например:

- `general-it`;
- `cpp-vtk`;
- `electromagnetics`;
- пользовательские профили.

Предусмотреть импорт терминов из кодовой базы проекта как отдельную необязательную утилиту. Для C++-репозитория полезно извлекать имена классов, функций, namespace, типов, CMake targets и названия библиотек. Не сканировать и не загружать кодовую базу автоматически без явного указания пути.

Использовать prompt/context ASR только как дополнительный механизм. Не подменять им постобработку.

### 3.6. LLM post-processing

LLM является необязательным последующим этапом и не должна быть необходима для получения транскрипта.

Назначение:

- формирование протокола совещания;
- извлечение решений, задач, сроков и ответственных;
- группировка обсуждения по темам;
- подготовка краткого резюме;
- помощь в разрешении неоднозначных терминов, но не произвольное переписывание транскрипта.

Интеграцию реализовать через абстрактный интерфейс. Для MVP предусмотреть локальный OpenAI-compatible endpoint (например, LM Studio или llama.cpp server), настраиваемый через конфигурацию. Не включать большую LLM в тот же GPU inference process по умолчанию.

LLM должна получать транскрипт с `speaker_id` и timestamps. Ей запрещено придумывать отсутствующие реплики, имена участников, решения, сроки и ответственных. Неуверенные выводы помечать как требующие проверки.

## 4. Контракт данных

Основной внутренний формат — JSON. Хранить как минимум:

- metadata исходного аудио;
- параметры запуска и версии моделей;
- raw ASR transcript;
- diarization segments;
- aligned transcript;
- corrected transcript;
- список терминологических замен;
- confidence/quality flags, если доступны;
- ошибки и предупреждения pipeline.

Пример структуры:

```json
{
  "meeting_id": "meeting_001",
  "language": "ru",
  "source_audio": {
    "filename": "meeting.wav",
    "duration": 3600.0,
    "sample_rate": 48000,
    "channels": 2
  },
  "speakers": [
    {
      "speaker_id": "speaker_00",
      "display_name": null
    }
  ],
  "segments": [
    {
      "start": 12.34,
      "end": 16.82,
      "speaker_id": "speaker_00",
      "raw_text": "Нужно проверить витэка чарт икс уай.",
      "corrected_text": "Нужно проверить vtkChartXY.",
      "words": [],
      "corrections": [
        {
          "source": "витэка чарт икс уай",
          "target": "vtkChartXY",
          "term_id": "vtkChartXY",
          "confidence": 0.93
        }
      ],
      "quality_flags": []
    }
  ],
  "models": {
    "asr": "model-id-and-revision",
    "diarization": "model-id-and-revision"
  }
}
```

Это иллюстративная схема: уточнить окончательную структуру с учётом реальных выходов библиотек.

Требования к хранению:

- исходная запись никогда не изменяется;
- raw transcript неизменяем;
- corrected transcript создаётся отдельно;
- исправления аудируемы;
- повторный запуск с другими параметрами не перезаписывает результаты без явного флага;
- сохранять конфигурацию, версии библиотек, идентификаторы/хеши моделей и дату обработки.

## 5. VRAM и режим выполнения

Целевое тестовое оборудование — NVIDIA GPU с 8 ГБ VRAM. Система должна также масштабироваться на GPU с большей памятью.

Основной режим MVP — последовательное выполнение ASR и diarization на одной GPU:

1. загрузить ASR;
2. обработать аудио пакетами/сегментами;
3. сохранить результат;
4. освободить модель и GPU memory;
5. загрузить diarization;
6. выполнить diarization;
7. объединить результаты на CPU.

Не полагаться только на `torch.cuda.empty_cache()` как на способ освобождения памяти: корректно освобождать ссылки на модели и проверять фактическое потребление VRAM.

Настройки должны быть конфигурируемыми:

- `device`;
- `compute_type`/precision;
- `batch_size`;
- размер аудиосегмента;
- overlap между сегментами;
- максимальное число говорящих;
- число потоков CPU;
- временный каталог;
- лимит памяти/параллелизма.

Не фиксировать неподтверждённые значения как универсальные. Подобрать defaults тестами на 8 ГБ и документировать альтернативы для более мощных GPU.

## 6. Полностью локальная загрузка моделей

Создать отдельные скрипты для получения моделей. Runtime не должен скачивать веса.

Требования к скриптам:

- `scripts/download_models.sh` — единая точка входа;
- отдельные скрипты/модули для каждой модели;
- явные версии и revision/commit, где источник это поддерживает;
- загрузка только из официальных или проверенных источников;
- контрольные суммы SHA-256 после загрузки;
- проверка наличия и целостности уже загруженных файлов;
- возможность указать собственный каталог моделей;
- повторный запуск без повторной загрузки корректных файлов;
- понятная ошибка при недоступности источника или изменении структуры файлов;
- лицензии и условия использования сохранять рядом с моделью.

Для каждой модели в `models/README.md` зафиксировать:

- точное имя модели;
- официальный источник;
- ссылку на карточку/документацию;
- версию/revision;
- лицензию;
- формат файлов;
- ожидаемый размер;
- способ загрузки;
- способ локальной загрузки в runtime;
- проверенную конфигурацию GPU;
- известные ограничения.

Если checkpoint доступен только через Hugging Face, разрешается использовать Hugging Face как источник первоначального получения весов, но не как runtime dependency. Если модель gated или требует токен, сначала искать альтернативу без авторизации. Если подходящей альтернативы нет — явно описать это и не скрывать ограничение.

Для `faster-whisper` проверить, как получить и хранить CTranslate2-модель локально. Не допускать, чтобы `WhisperModel` при старте контейнера пытался разрешить идентификатор модели через Hub. Альтернативно оценить `whisper.cpp` с локальным GGML/GGUF checkpoint. Выбрать один backend для MVP и обосновать выбор.

## 8. Docker и развёртывание

Подготовить Docker image для инференса с NVIDIA GPU.

Требования:

- выбрать совместимую базу CUDA/PyTorch/NeMo после проверки официальных compatibility matrix;
- не использовать `latest` для базового образа и критичных зависимостей;
- закрепить версии зависимостей;
- предусмотреть сборку образа без скачивания моделей;
- модели подключать как read-only volume;
- входные и выходные каталоги подключать как volumes;
- не помещать веса моделей внутрь image по умолчанию;
- запускать контейнер от непривилегированного пользователя, если это совместимо с доступом к GPU и файловым томам;
- поддержать `docker compose` и `--gpus all`;
- не публиковать сетевые порты, если они не нужны;
- по умолчанию не требовать интернет-доступа;
- обеспечить graceful error при несовместимой CUDA или отсутствии GPU.

Пример ожидаемого интерфейса:

```bash
docker compose run --rm transcriber \
  transcribe /data/input/meeting.wav \
  --config /app/config/default.yaml
```

Команду и формат CLI уточнить при реализации. Обеспечить отдельные команды:

```bash
./scripts/download_models.sh
./scripts/verify_models.sh
./scripts/build_image.sh
./scripts/offline_smoke_test.sh
```

Модели должны скачиваться на host в `models/`, затем монтироваться в контейнер. Runtime должен работать при отсутствии сетевого подключения.

## 10. Проверка качества

Создать воспроизводимый evaluation workflow.

### 10.1. ASR

На вручную проверенной эталонной записи измерять:

- WER;
- при необходимости CER;
- точность технических терминов;
- качество английских терминов внутри русских предложений;
- качество названий классов, библиотек и идентификаторов;
- влияние terminology prompt и post-correction.

Не сравнивать модели только по английским leaderboard результатам.

### 10.2. Diarization

Измерять:

- DER;
- confusion между говорящими;
- missed speech;
- false alarm;
- устойчивость определения участников на коротких репликах;
- качество при частичном overlap.

Проверить автоматическое определение количества участников на записи с 8–15 людьми. Если оценка количества говорящих нестабильна, документировать возможность ручного `num_speakers`.

### 10.3. End-to-end

Проверить:

- корректность временных меток;
- правильность привязки текста к говорящему;
- сохранение параллельных реплик;
- отсутствие потери сегментов на границах чанков;
- корректность JSON, Markdown и SRT;
- отсутствие выдуманных терминологических исправлений.

Создать небольшой тестовый набор с разрешёнными для использования аудиофрагментами. Не включать реальные конфиденциальные совещания в репозиторий.

## 11. Этапы реализации

## 12. Критерии приёмки

Работа считается завершённой, если:

1. Репозиторий содержит все исходники, скрипты, конфиги, Dockerfile, Compose и документацию.
2. Модели можно загрузить отдельной командой и проверить по SHA-256.
3. Runtime не обращается к Hugging Face Hub и не требует HF token.
4. После подготовки зависимостей и моделей pipeline запускается без интернета.
5. ASR распознаёт русскую речь и сохраняет английские технические фрагменты настолько корректно, насколько позволяет выбранная модель.
6. Diarization работает с конфигурацией для 8–15 участников, без фиксированного лимита в четыре.
7. ASR и diarization могут выполняться последовательно на GPU с 8 ГБ VRAM; фактические настройки и пиковое потребление документированы.
8. Результат содержит raw transcript, corrected transcript, speaker IDs и timestamps.
9. Все терминологические исправления аудируемы и могут быть отключены.
10. LLM post-processing необязателен и работает через локальный endpoint.
11. Docker image собирается воспроизводимо, а модели не встраиваются в него по умолчанию.
12. Есть unit/integration/smoke tests и инструкция запуска.

## 13. Ограничения и инженерные предостережения

- Не обещать идеальную diarization при перекрывающейся речи: качество зависит от записи, микрофонов, акустики и длительности реплик.
- Не считать speaker ID реальным именем человека. Сопоставление `speaker_XX` с именами должно быть отдельной ручной функцией.
- Не выполнять безусловные замены терминов по fuzzy match.
- Не позволять LLM менять смысл исходной речи.
- Не загружать все модели одновременно на GPU с 8 ГБ.
- Не фиксировать несовместимые версии PyTorch, CUDA, NeMo и CTranslate2 без проверки.
- Не добавлять неиспользуемые сервисы, веб-интерфейс, базу данных или message broker в MVP.
- Не коммитить веса, персональные записи и секреты.
- Все неподтверждённые технические предположения фиксировать в `docs/known-limitations.md`.
